Lesson 0034 · Intervals & Greedy

Intervals & Greedy — Sort, Sweep, Exchange

Most interval problems start the same way: sort by one endpoint, then sweep once. The art is proving the greedy choice is safe.

Interval problems — merging, overlap-counting, room scheduling — almost all reduce to sort, then a single linear sweep. The decision is which endpoint to sort by: sort by start to merge or detect overlaps, by end to maximise non-overlapping picks. Greedy more broadly means "make the locally best choice and never revisit it" — fast and simple, but only correct when you can prove the local choice is globally safe.

The Staff-level skill here is the exchange argument: to justify a greedy choice, show that any optimal solution can be transformed to use your greedy pick without getting worse. "Sort by earliest end time, always take the first compatible interval — because swapping in the earliest-finishing one never reduces how many remain." Saying that proof out loud is exactly the "why is this optimal?" bar Google probes. A greedy without a justification is a guess.

The sort-and-sweep template

Arrays.sort(intervals, (a, b) -> a[0] - b[0]);   // by start (merge/overlap)
// or                  (a, b) -> a[1] - b[1];    // by end   (max non-overlapping)
int prevEnd = intervals[0][1];
for (int i = 1; i < intervals.length; i++) {
    if (intervals[i][0] < prevEnd) {             // overlap
        // merge: prevEnd = max(prevEnd, intervals[i][1]);
        // or count a conflict / drop one
    } else {
        prevEnd = intervals[i][1];               // disjoint, advance
    }
}
Pattern signals. "merge overlapping …", "insert an interval", "minimum meeting rooms", "non-overlapping intervals to remove", "can attend all meetings", "minimum number of arrows / platforms". For pure greedy: "jump game", "gas station", "assign tasks / cookies" — anything where a sort plus one sweep with a locally-best rule looks plausible.

Check your model first

Drill — three problems

Drill 1 — merge by start LeetCode 56 · Merge Intervals

Merge all overlapping intervals.

Hint

Sort by start. Walk through; if the current interval starts at or before the last merged end, extend that end; otherwise push a new interval.

Solution (Java) 
public int[][] merge(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[0] - b[0]);
    List<int[]> out = new ArrayList<>();
    int[] cur = intervals[0];
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] <= cur[1]) {              // overlap → extend
            cur[1] = Math.max(cur[1], intervals[i][1]);
        } else {
            out.add(cur); cur = intervals[i];         // disjoint → commit, restart
        }
    }
    out.add(cur);
    return out.toArray(new int[0][]);
}

Time O(n log n) · Space O(n). Insight: sorting by start guarantees any interval that could merge with cur appears contiguously — that's why a single pass suffices and you never look backward.

Drill 2 — sweep / heap for rooms LeetCode 253 · Meeting Rooms II

Minimum number of rooms to host all meetings without conflict.

Hint

Min-heap of end times. Sort by start; for each meeting, if the earliest-ending room is free (its end ≤ this start) reuse it (poll), else allocate a room. Heap size is the answer.

Solution (Java) 
public int minMeetingRooms(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[0] - b[0]);
    PriorityQueue<Integer> ends = new PriorityQueue<>();   // min-heap of end times
    for (int[] m : intervals) {
        if (!ends.isEmpty() && ends.peek() <= m[0]) ends.poll();  // reuse a freed room
        ends.offer(m[1]);
    }
    return ends.size();
}

Time O(n log n) · Space O(n). Insight: the heap tracks when rooms free up; its peak size is the max simultaneous overlap — this is where intervals meet the heap module. A two-pointer sweep over sorted starts and ends is an equivalent O(n log n) alternative.

Drill 3 — greedy by end LeetCode 435 · Non-overlapping Intervals

Minimum intervals to remove so the rest don't overlap.

Hint

Sort by end. Greedily keep an interval whenever it starts at or after the last kept end; otherwise it overlaps and must be removed. Count removals.

Solution (Java) 
public int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[1] - b[1]);    // by END
    int kept = 0, prevEnd = Integer.MIN_VALUE;
    for (int[] iv : intervals) {
        if (iv[0] >= prevEnd) { kept++; prevEnd = iv[1]; }  // compatible → keep
    }
    return intervals.length - kept;
}

Time O(n log n) · Space O(1). Insight: sort-by-end is the classic activity-selection greedy — keeping the earliest finisher leaves the most room for the rest. The exchange argument (swapping in the earliest end never hurts) is what makes it provably optimal.
